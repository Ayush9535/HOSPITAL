## 2. Isolation invariants (non-negotiable, checked on every PR)

1. **No OT controller is ever added to a `/clinic/**` or `/pharmacy/**` alias list.**
2. **OT never adds a column to a clinic-aliased table** — `patients`, `wards`, `beds`, `billing`, `appointments`, `doctors`, `opd`. Where OT needs their behaviour (e.g. bed vacate → cleaning), it calls the existing service **through a hospital-only facade, unchanged**.
3. Every new OT table carries `hospital_id NOT NULL` + FK, and is written only by OT services.
4. Every OT controller carries `@TenantType(HOSPITAL)` **and** `@RequireModule("OT")`, both enforced by `@within`.
5. Tenant scope is asserted **in the service**, via `SecurityHelper.getCurrentHospitalId()` — never in the controller, because 22 controllers are shared.
6. Any change to a shared service requires the Clinic + Pharmacy regression suite to pass **unmodified**.

## 3. Decisions

### D1 — Isolation becomes a server-side invariant (Phase 0A), and **the module gate is scoped to HOSPITAL tenants**
`hospitalType` becomes a JWT claim; a new `@TenantType` aspect and a corrected `ModuleAccessAspect` both match `@annotation` **and** `@within`; the `/clinic`,`/pharmacy` aliases are stripped from `OtInchargeController`.

**Critically (F16): `ModuleAccessAspect` enforces only when `hospitalType == HOSPITAL`.** Clinic and Pharmacy skip the module check entirely.

```java
if (details.getHospitalId() == null) return;                 // Super Admin — unchanged
if (details.getHospitalType() != HospitalType.HOSPITAL) return;  // F16: Clinic/Pharmacy keep today's behaviour
if (enabledModules == null || !enabledModules.contains(required)) throw new UnauthorizedException(...);
```

**Why:** module gating was designed for hospital plans, and Clinic/Pharmacy have **never** had it enforced. Skipping preserves their behaviour byte-for-byte (the mandate) while OT and NURSING gates begin working for hospitals immediately. Without this scope, the "fix" permanently breaks three pharmacy endpoints and one clinic endpoint whose modules those tenants *cannot be granted* (F16). Whether Clinic should have module enforcement is then a **separate, deliberate decision**, not an accident of an AOP correction.
**Rejected:** widening the CLINIC/PHARMACY plan catalogs and backfilling every live plan (any missed tenant 403s in production); removing the three aliases (deletes endpoints Clinic and Pharmacy use today).
**Also rejected:** a database per tenant type (F3 is an *enforcement* gap, not a *storage* gap); a separate codebase (defeats the goal).

### D2 — Authorization binds to **permissions on the existing role string**, not to a new designation entity
`permissions` (master) + `role_permissions(hospital_id, role, permission_code)`. `JwtAuthenticationFilter` mints permission authorities **alongside** `ROLE_*`, so `@PreAuthorize("hasAuthority('OT_SCHEDULE'))"` works with **zero new infrastructure** — no custom `PermissionEvaluator`.
**Why:** F12 — the HMS has no designation concept at all. Introducing `staff_designations` now is a second project, exactly as the reviewer warned. Binding permissions to the role string we already have delivers 100% of Principle 2 (workflow never knows *who*) at ~2 tables.
**A "new designation" today** = a new role string + its `role_permissions` rows. A first-class designation master is deferred to Phase 8 and is a **rename**, not a redesign, because nothing will reference the role string except this one mapping table.
**Day-1 seed reproduces current behaviour byte-for-byte** (`DOCTOR→OT_CREATE`, `RECEPTIONIST→OT_SCHEDULE|OT_START|OT_COMPLETE|OT_CANCEL`, `NURSE→OT_PRE_OP`). Nothing changes until a hospital reassigns a permission.

### D3 — Workflow policy is separate from both, and lazy-defaulted
`ot_workflow_policies(hospital_id, policy_key, priority_scope, value)`. Absent row = default. The engine reads **policy only** and never learns a role; authorization reads **permissions only** and never learns a step.
**Why:** this is Principle 2 made structural. The lazy-default pattern is already proven twice here (`FormAccessService`, `VitalSettingsService`); a third pattern would be a liability.

### D4 — Emergency is a `priority_scope`, not a flow. Reschedule is a transition, not a state.
Policy resolves on `(hospital_id, policy_key, priority_scope ∈ {ANY, ELECTIVE, EMERGENCY})`. Emergency simply resolves `APPROVAL_MODE=NONE`, `CONSENT=DEFERRED`.
Reschedule is `SCHEDULED → SCHEDULED` **recorded in `surgery_state_transitions`** with a reason and the old/new slot in the payload.
**Why:** a parallel emergency flow duplicates every guard and guarantees divergence. A `RESCHEDULED` state doubles the machine and makes "how many cases today" a two-clause query. **`surgery_schedule_versions` is therefore cancelled** — the transition table already is the history.

### D5 — The case state machine (revised: `IN_THEATRE` removed)

```
REQUESTED → APPROVED → SCHEDULED → PRE_OP → IN_PROGRESS → COMPLETED → CLOSED
terminal: CANCELLED          loop: POSTPONED → APPROVED
```

**`IN_THEATRE` is deleted.** Patient arrival in theatre is the milestone `PATIENT_ENTERED_OT`.
**Why:** it added a state whose only content was a timestamp. States must gate legal actions; timestamps are facts. This is the same test that kills `RESCHEDULED` and `IN_RECOVERY`.

### D6 — The **waiting list is `APPROVED` without a schedule** — a derived view, not a state
Waitlist ordering data (`waitlist_priority`, `target_date`, `approved_at`) are **attributes on `surgeries`**.
**Why:** hospitals approve 100 and schedule 20 — so `APPROVED` is *precisely* the waiting list. Adding `WAITLISTED` would make `APPROVED` a state that lasts microseconds and exists only to be left. The requirement is real; a new state is not the way to meet it. This is consistent with D4/D5: **if it is answerable by a query, it is not a state.**

### D7 — `CLOSED` means *clinical documentation complete and patient dispositioned* — never billing, never discharge
Policy `CLOSE_REQUIRES` ⊆ `{OPERATIVE_NOTE, WHO_SIGN_OUT, DISPOSITION}`; small hospitals default to `{}`.
**Why:** the closure criterion was genuinely undefined. Coupling closure to **billing** means an unpaid bill keeps an OT case open forever and corrupts throughput metrics; coupling it to **discharge** means a case stays open for days after the theatre is free. Billing and discharge are other modules with their own lifecycles. OT closes when OT's obligations are met.

### D8 — Recovery and Transfer are milestones (+ an optional PACU episode), never case states
`RECOVERY_TRACKING = NONE | MILESTONE | PACU_EPISODE`.
**Why:** the theatre is turned over while the patient is still in PACU. A case state of `IN_RECOVERY` keeps the room *logically* busy while it is physically free, destroying utilisation — the metric that justifies the module.

### D9 — Rooms start simple; the occupancy timeline is deferred
MVP `ot_rooms(id, hospital_id, name, status, current_surgery_id, turnover_minutes)`. `ot_room_occupancy` is **Phase 9**.
**Why:** the F7 heuristic must die immediately; the timeline is an analytics nicety. Until it exists, utilisation is derived from `surgery_state_transitions`, which is accurate enough and free.
Migration is **proposed, never automatic** — an admin confirms which OT-named wards become rooms (`"FOOT WARD"`).

### D10 — Surgeon double-booking is a **query**, not a module
On schedule, reject an overlapping interval for the same `surgeon_doctor_id`. Room conflicts use a **pessimistic lock on the room row** plus an overlap query (a unique index cannot express interval overlap).
**Why:** F13 — no leave/availability entity exists. Full leave management is a backlog item; 90% of the harm (same surgeon, three rooms, same time) is prevented by one query and costs nothing.

### D11 — Forms are procedure-scoped, signed, immutable, versioned
`UNIQUE(surgery_id, form_type)`. A signed form is never updated; an edit appends a version. `performed_by` and `recorded_by` are separate fields (reusing `PerformingNurseResolver`).
**Why:** F8 is a data-loss and litigation risk. Confirmed by the user: one admission may carry several surgeries, each needing its own consent, WHO checklist, and operative note.

### D12 — Forms stay JSON, with the measured fields **promoted to columns**
`data_json` remains the record for layout-driven fields; ~8 fields that are **reported on or blocked on** become real columns (`sign_in_at`, `time_out_at`, `sign_out_at`, `counts_correct`, `site_marked`, `signed_at`, `signed_by`, `version`).
**Why:** never report from a blob; never migrate 15 tables to avoid it.

### D13 — **Surgery is its own aggregate. IPD admission is optional.** (Q4 = yes, day-care)
`surgeries.ipd_admission_id` becomes **nullable**; `patient_id` is the anchor; `encounter_type ∈ {IPD, DAY_CARE}`.
**Why (the biggest decision in this document):** the reviewer is right that this is far larger than it looks and far cheaper now than later. Cataract, endoscopy, and minor orthopaedic cases do not admit. If OT stays coupled to IPD:
- every future procedure room (cath lab, endoscopy, day-care) needs a fake admission;
- `surgery_forms` remains keyed to an admission that may not exist;
- billing for a day-care case has no home.
Making the admission optional **now** costs one nullable column and one guard; making it optional **after** Phase 4 costs a migration of every OT table plus every UI that assumes `IpdDetails` is the entry point.
**Consequence:** OT gains its own patient-entry path (reception books a day-care surgery for a registered patient); `IpdDetails` remains *an* entry point, not *the* entry point.

### D14 — Analytics ships with the policy engine (Phase 5), not at the end
Basic four — today's surgeries, completed, cancelled (by reason), utilisation — are queries over `surgery_state_transitions`.
**Why:** they are the first thing a hospital owner asks for, and by Phase 5 the transition table already contains every fact they need. Deferring them to Phase 9 withholds value that costs one controller.

### D15 — OT billing never touches the `billing` table's schema
A hospital-only `surgery_charges` table accumulates OT/consumable/implant charges and posts them through the **existing** billing API.
**Why:** invariant #2. `billing` is clinic-aliased; adding `surgery_id` to it would put OT columns in Clinic's tables.

### D16 — The OT Calendar extends `HospitalCalendarService`; it is not a new module
F15 — surgeries are already a layer there. OT adds a **room axis** and a day drill-down. The **OT List** (today's list: patient, age, procedure, room, time, surgeon) is a print view over the same query, reusing `PdfLayoutHelper`.
**Why:** a second calendar would immediately diverge from the first.

| | `surgery_charges` (D15) |
| | `doctor_leave` (D10) |
| | ~~`surgery_schedule_versions`~~ — **cancelled** (D4) |
| | ~~`permissions`~~ — **cancelled**, see below |
| | ~~`cancellation_reasons`~~ — **cancelled**, see below |

**Two tables were cancelled during implementation**, both replaced by the codebase's existing
registry pattern (`FormRegistry`, `VitalRegistry`):

- **`permissions`** → `security/OtPermissions`. The codes are compile-time constants that endpoints
  reference by name; a table would let a row exist for a permission no endpoint honours. Only the
  hospital's *overrides* need storage, which is `role_permissions`.
- **`cancellation_reasons`** → `service/hospital/ot/CancellationReasons`. NABH reports
  "% elective cancellations **by reason**" across hospitals, so the taxonomy must **not** vary per
  tenant. Per-hospital custom reasons can be layered on later exactly as custom vitals were.

MVP table count: **8 → 6.**

Columns added to `surgeries` (hospital-only table): `ot_room_id`, `encounter_type`, `waitlist_priority`, `target_date`, `approved_at`, `estimated_duration_minutes`, `laterality`, `anaesthesia_type`.

## 5. Rejected, and why

| Rejected | Why |
|---|---|
| A BPM engine (Camunda/Flowable) | 9 states. A second runtime and data model is a permanent tax. |
| A database per tenant type | F3 is an enforcement gap, not a storage gap. |
| `staff_designations` in the MVP | F12 — no designation concept exists; it is a separate project (reviewer, #3). |
| `WAITLISTED`, `RESCHEDULED`, `IN_THEATRE`, `IN_RECOVERY` states | Each is answerable by a query or a timestamp (D5, D6). |
| A separate emergency workflow | Duplicates every guard; priority-scoped policy is equivalent and free. |
| `surgery_schedule_versions` | The transition table already is the history (D4). |
| Custom Spring `PermissionEvaluator` | Minting permission authorities makes `hasAuthority` work natively. |
| Full normalisation of the 15 NABH forms | Hybrid (D12) buys reportability without a 15-table migration. |
| OT settings inside `HospitalAdminDashboard.jsx` | Already ~3000 lines. |
| Blocking OT development on the security work | Phase 0A is days; it does not gate Phase 1+ (reviewer, #2). |
